# Requirements and Quality Analysis

## Functional Requirements
| Number   | Requirement                                                                                                                            |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| *FR-01*  | The application shall allow a developer to create a project by providing a project name and description.				                |
| *FR-02*  | The system shall allow a developer to view and update the information of an existing project.                                          |
| *FR-03*  | The system shall allow a developer to create a playtest session associated with an existing project, supplying a session name, date, and game version.                                                                                                                                   |
| *FR-04*  | The application shall allow a developer to view and update the status and details of an existing playtest session.                     |
| *FR-05*  | The system shall allow a playtester to submit feedback associated with a specific playtest session, including a title and description. |
| *FR-06*  | The system shall require feedback classified as a defect to additionally capture expected behaviour, actual behaviour, reproduction steps, and environment information.                                                                                                                 |
| *FR-07*  | The system shall allow feedback to be categorised according to its type, including defect, usability, gameplay, balance, accessibility, or feature request.                                                                                                                                 |
| *FR-08*  | The application shall allow developers to assign a priority to identified issues.                                                      |
| *FR-09*  | The application shall allow developers to update the status of identified issues throughout the resolution process.                    |
| *FR-10*  | The system shall allow developers to view submitted feedback and its associated information.                                           |
| *FR-11*  | The application shall allow developers to filter feedback based on attributes such as status, priority, category, or playtest session. |
| *FR-12*  | The system shall provide developers with an overview of recorded playtesting feedback, including summary information about feedback categories, issue statuses, priorities, and playtest activity.                                                                                      |
| *FR-13*  | The application shall allow developers to delete projects, playtest sessions, and feedback records. The application shall require confirmation before deletion and shall cascade deletion to associated records where applicable.                                                     |

## Requirements Quality Analysis 
A quality analysis of the written requirements was completed prior to the finalised versions seen above. This analysis crossed six criteria categories - clarity, completeness, consistency, correctness, feasibility, and testability.

**Clarity**  
The requirements were reviewed for clarity and ambiguity to ensure expected system behaviour was communicated precisely. Requirements use consistent terminology and describe observable system or user actions to reduce potential uncertainty during implementation and testing. Where the original wording could be interpreted in multiple ways, such as the deletion of content in FR-13, additional detail was added to clarify the expected behaviour. Similar refinements were made to FR-05, FR-06, NFR-01 and NFR-02, as documented in the Improved Requirements section.

**Completeness**  
Requirement completeness was also evaluated to ascertain that the intended system behaviour was sufficiently represented across projects, playtest sessions, feedback, issue management, and the quality overview. The requirements were checked against the scope established in Task 1 to ensure the core workflow was captured. Where information was considered insufficient, such as FR-12, the requirement was expanded to specify that the quality overview would include categories, statuses, priorities and playtest activity. Completeness was considered within the constraints of the defined project scope. Functionality such as advanced authentication, external integrations, and real-time collaboration were purposefully excluded as these features are deemed outside the scope defined for the prototype.

**Consistency**  
Consistency across requirements was assessed to ensure consistent formatting, cohesion between related requirements, and the absence of apparent contradictions. Requirements use consistent terminology, tone and structure, with system and user actions described comparatively throughout. Related requirements were also reviewed to ensure that their responsibilities did not unnecessarily overlap. For example, FR-05 establishes the common information required when submitting feedback, while FR-06 defines the additional information required when that feedback is classified as a defect. This clear separation avoids duplication while maintaining a consistent relationship between general feedback and defect-specific information.

**Correctness**  
Requirements were compared to the proposed scope to confirm that the intended system was described accurately. The requirements correctly represent a system designed to address the scattered, inconsistent, and incomplete playtesting feedback identified in the problem statement through structured feedback collection (FR-05 → FR-07), issue prioritisation and status tracking (FR-08 → FR-09), feedback review and filtering (FR-10 → FR-11), and quality overview functionality (FR-12). The requirements therefore remain aligned with the problem identified and the core functionality defined within the proposed scope.

**Feasibility**  
The scope and requirements were reviewed to determine whether they could be implemented and tested during a single semester by an individual using the specified React, ASP.NET Core/C#, and SQLite technologies. The core workflow represented by the requirements is considered manageable within the available timeframe, particularly given the deliberately limited prototype scope and the use of AI-assisted development tools to support implementation and learning. Time-consuming or technically complex features, including authentication, real-time collaboration, and cloud infrastructure, have explicitly been excluded from the prototype scope, as they are not necessary to demonstrate the core proposed solution and would significantly increase implementation complexity beyond the defined scope.  Features such as the quality overview can also be developed progressively, beginning with the required core functionality before additional visualisation or metric capabilities are introduced.

**Testability**  
The testability of the requirements was evaluated by considering whether their expected outcomes could be objectively observed or measured. For example, the confirmation of a delete action and cascade deletion are both observable and testable outcomes of FR-13. Similarly, the presence of required fields for defect feedback (FR-06) and the ability for developers to update issue status (FR-09) can directly be verified through functional testing. The non-functional requirements also include measurable or verifiable criteria: a response time of ≤ 2 seconds can be measured (NFR-01), operation within a specified Chrome and Windows environment can be verified (NFR-03), and successful execution using the documented dependencies and setup process (NFR-06) can be verified as well.


## Improved Requirements
Following the requirements quality analysis, certain requirements were refined to improve clarity, completeness, consistency, and testability. A focus was placed on removing ambiguity from wording, outlining required information and behaviour, and adding measurable criteria where possible.

| Requirement | Initial wording | Improved wording | Reason for improvement |
| ----------- | --------------- | ---------------- | ---------------------- |
| *FR-05*     | The system shall allow players to submit feedback associated with a given playtest session. | The system shall allow a playtester to submit feedback associated with a specific playtest session, **including a title and description.** | The original identified the core function but did not specify the minimum information required for a feedback record. |
| *FR-06*     | The system shall allow feedback classified as a defect to capture a title, description, expected behaviour, reproduction steps, and environment information. | The system shall **require feedback classified as a defect to additionally capture** expected behaviour, actual behaviour, reproduction steps, and environment information. | Title and description are now defined as common feedback fields under FR-05, while FR-06 clearly identifies the additional information required specifically for defects. |
| *FR-12*     | The system shall display an overview of recorded playtesting feedback and their status. | The system shall provide developers with an overview of recorded playtesting feedback, including summary information about **feedback categories, issue statuses, priorities, and playtest activity.** |"Overview" and "status" were considered too broad to fully define the expected dashboard content. The refinement identifies the information that must be represented. Also added specificity to who would be able to access the overview. |
| *FR-13*     | The application shall allow developers to delete projects, playtest sessions, and feedback records where deletion does not violate the integrity of associated records. | The application shall allow developers to delete projects, playtest sessions, and feedback records. The application shall **require confirmation before deletion** and shall **cascade deletion to associated records where applicable.** | The original requirement left the deletion behaviour ambiguous. The refinement defines the user confirmation and relationship behaviour, making the requirement directly testable. |
| *NFR-01*    | The system shall provide an appropriate response time for normal operations. | The system shall provide a response time of **no more than 2 seconds** for normal project, playtest session, feedback, and issue-management operations **under the defined prototype test environment.** | "Appropriate" was subjective. A measurable response-time threshold allows performance to be objectively evaluated.
| *NFR-02*    | The system shall reliably save valid project, playtest session, feedback, and issue data. | The application **shall successfully persist** valid project, playtest session, feedback, and issue data **across application restarts under normal operating conditions.** | "Reliably save" was difficult to assess objectively. The refinement identifies persistence across restarts as an observable reliability criterion. |


## Acceptance Criteria
| Number  | Criteria                                                                                                                                |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| *AC-01* | Given the developer is creating a new project, when a valid project name, description, and game version are provided and the form is submitted, then the system shall create the project and make it available for further management in the project list.                               |
| *AC-02* | Given an existing project, when the developer modifies its information and saves the changes, the system shall update the project and the new information will be displayed.                                                                                                              |
| *AC-03* | Given an existing project, when the developer provides a session name, date, and game version and submits the session, then the system shall create the playtest session and associate it with the selected project.                                                                       |
| *AC-04* | Given an existing playtest session, when the developer modifies its details or status and saves the changes, then the system shall update the session and display the updated information.                                                                                             |
| *AC-05* | Given an active playtest session, when a playtester provides a title, description and feedback category and submits the feedback, then the system shall create the feedback record and associate it with the selected playtest session.                                                    |
| *AC-06* | Given feedback is classified as a defect, when the playtester attempts to submit feedback, then the system shall require expected behaviour, actual behaviour, reproduction steps, and environment information before the feedback can be submitted.                                  |
| *AC-07* | Given an identified issue exists, when a developer assigns a priority or changes its status, then the system shall save and display the updated priority or status.                                                                                                                         |
| *AC-08* | Given feedback has been submitted, when a developer selects the feedback record, then the system shall display its associated information.                                                                                                                                        |
| *AC-09* | Given multiple feedback records exist, when a developer applies a filter based on status, priority, category, or playtest session, then the system shall display only records matching the selected criteria.                                                                               |
| *AC-10* | Given the project contains recorded playtesting data, when a developer accesses the quality overview, then the system shall display summary information covering feedback categories, issue statuses, priorities, and playtest activity.                                                |
| *AC-11* | Given a developer has selected a project, playtest session, or feedback record for deletion, when the developer chooses to delete it, then the system shall request confirmation before permanently deleting the record.                                                                  |
| *AC-12* | Given a deletion confirmation is displayed, when the developer cancels the deletion, then the selected record and its associated records shall remain unchanged.                                                                                                                             |
| *AC-13* | Given a project or playtest session contains associated records, when the developer confirms its deletion, then the system shall delete the selected record and its associated records according to the defined relationships.                                                              |
| *AC-14* | Given the application is operating within the defined prototype test environment, when a normal project, playtest session, feedback, or issue-management operation is performed, then the operation shall return a response within 2 seconds.                                               |
| *AC-15* | Given valid project, playtest session, feedback, or issue data has been saved, when the application is closed and restarted, then the previously saved data shall remain available and unchanged.                                                                                         |
| *AC-16* | Given the application is running in Google Chrome on the supported Windows development environment, when the core project, playtest session, feedback, and issue-management workflows are performed, then the workflows shall operate as specified.                                     |
| *AC-17* | Given a first-time user has access to the application and is provided with the task of creating a project, creating a playtest session, and submitting feedback, when the user attempts to complete these workflows using the application interface without developer assistance, then the user shall be able to complete all three workflows successfully.                                                                                    |
| *AC-18* | Given a user enters invalid or potentially unsafe input into a supported input field, when the user attempts to submit the input, then the application shall validate the input, prevent invalid data from being stored or processed where appropriate, and handle the input without causing an application error.                                                                                                                       |


## Software Quality Attributes
| Quality Attribute | Relevance to Checkpoint | Related NFRs |
| ----------------- | ----------------------- | ------------ |
| *Usability*       | Playtesters should be able to provide feedback in a straightforward manner without needing to understand complex terminology. Similarly, developers need to be able to efficiently find and manage issues within the system. For all users, forms should avoid unnecessary fields and interface clutter. | NFR-05 |
| *Reliability*     | To maintain accurate and reliable organisation of feedback, data must persist successfully within the system, including the relationships between projects, sessions and feedback. Preventing invalid data and appropriately handling errors also contributes to the reliability of the system. | NFR-02 |
| *Performance*     | Developers should be able to navigate, submit, filter, and manage feedback without significant delays. Project, playtest session, feedback, and issue-management operations should therefore complete within the defined response-time threshold. | NFR-01 |
| *Maintainability* | To support future development and extension, the frontend, backend, and data-persistence components should be separated through clear architectural boundaries. This separation of concerns should make individual components easier to modify and maintain. | NFR-04 |
| *Security*    | As a locally hosted application, the primary security consideration within the prototype scope is the safe handling of user-provided data. Input should be validated and sanitised to reduce the risk of malformed or potentially malicious data affecting application behaviour or database operations.| NFR-07 |
| *Compatibility*   | The prototype needs to operate reliably within its defined browser and operating-system environment so that its functionality can be consistently demonstrated and tested. | NFR-03 |
